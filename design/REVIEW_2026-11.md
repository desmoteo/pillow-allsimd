# Review of 2026-11-03: code, documentation, process

A review of what the fork adds to Pillow 13.0.0 (154 files, about 29,000
lines), made after the first PyPI releases, to decide the next work. The
findings are numbered as in the review; the checkboxes track them.

## Verdict

The fork is in good shape. What usually goes wrong in a SIMD fork is
handled: every SIMD kernel has a scalar definition it must match, fast mode
is a separate, documented, bounded and deterministic path rather than an
"approximately the same" one, the build selects instruction sets
explicitly, and the tests pin the upstream tests that depend on Pillow's
exact arithmetic instead of changing their expected values. The weaknesses
are in maintainability (the cost of merging Pillow releases) and in the
release process, not in correctness.

What is done well, to keep:

- The fast-mode contract (`docs/reference/fast_mode.rst`): exact when off,
  deterministic, bounded, same shape, not stable across versions; each row
  of the table gives the mechanism, the speed-up and the error bound.
  `Fast.c` reads the flag atomically.
- Every build gives the same pixels: each fast kernel's header names the
  portable C function that defines its result, and `checks/simd_hashes.py`
  compares the builds.
- The test pinning in `Tests/conftest.py` (`EXACT_KERNEL_TESTS`) and the
  exact-mode hopper images in `Tests/helper.py`.
- The build configuration (`setup.py`): `-C simd=` validated per target,
  `-ffp-contract=off` with `native`, `-mfpmath=sse` on 32-bit x86, flags
  appended rather than replacing Python's, universal2 handled.
- The documentation: Pillow's pages intact, the fork's additions marked,
  the credits and the banner saying whose documentation it is; the design
  documents all listed in the README.
- Details: the glyph cache's 8 MB cap and its clearing on size and
  variation changes; the flood fill's heap stack with checked growth; the
  in-place alpha composite falling back when the images share memory.

## Findings

### Code

- [x] **1. `fast_mode()` restores a process-wide setting from one thread.**
      Two threads nesting `fast_mode()` blocks restore in interleaved
      order and can leave the process in the wrong mode. Fix: make the
      block's setting a thread-local override (`Fast.c`): `set_fast()`
      sets the process default, `fast_mode()` the current thread, and
      `get_fast()` returns the thread's effective setting. The
      free-threaded wheels (3.14t, 3.15t) make this more than theoretical.
- [x] **2. `resize()` reads the fast flag twice**, in Python for the
      `reducing_gap` default and in `ImagingResample`, while the docs
      promise one read per operation. Fix: pass the Python-side decision
      down to the C resize, so a `set_fast()` from another thread between
      the two reads can't mix kernels.
- [ ] **3. Merge cost: SIMD code inlined in Pillow's own files.** `Convert.c`
      has 24 `#if IMAGING_SIMD_*` blocks and 1,111 added lines; `BoxBlur.c`,
      `Geometry.c`, `Draw.c`, `Point.c` and `ZipEncode.c` are similar. The
      resample and filter kernels use the other convention, a separate
      `*SIMD*.c` included from the scalar file. Since each Pillow release
      is merged, the inline files conflict on every merge. Move the large
      inline blocks into companion files, with the scalar file gaining a
      call and an `#include` only. Not urgent; it compounds.
- [x] **4. `EXACT_KERNEL_TESTS` could go stale silently.** If upstream
      renames a pinned test, the pin stops matching and the test runs in
      fast mode, possibly passing by luck. Fix: a collection hook that
      fails the session when an entry matches no collected test.
- [x] **5. Readability.** `encoder_args == self.mode != "1"` (a chained
      comparison that reads as a typo) and `static INT32 inline` (legal,
      odd order). Rewrite both.

### Documentation

- [ ] **6. No explanation of how the kernels work for contributors.** The
      design documents cover decisions, not code. `SIMD_EXPLAINER_PLAN.md`
      plans it; write it as a Sphinx page under `docs/`, where a second
      contributor finds it. In progress: `docs/allsimd-kernels.rst`, with
      the ground rules and resampling (2026-11-03), the blurs, the kernel
      filters, the rank filters, the colour conversions, compositing and the
      channel operations (2026-11-04); the other sections follow the
      plan's order.
- [ ] **7. The speed-up tables are kept by hand** in `fast_mode.rst`, the
      README and `PyPI.rst`, while the chart is generated from the perf
      repository's data. Generate the tables too, so they can't drift.

### Release and CI

- [x] **8. Every push ran the full test matrix twice**, once per branch,
      because the same commit goes to `simd/pillow-13` and `simd/master`
      and the workflows trigger on `branches: "**"`. That was 14 macOS
      arm64 jobs per push competing with the release for runners, which is
      what blocked 13.0.0.post2 on 2026-11-03. Fix: the workflows skip
      `simd/master`.
- [x] **9. The release was all-or-nothing on 22 files.** One cancelled
      macOS job blocked the source package and the 14 Linux wheels that
      had passed. PyPI accepts files for an existing version. Fix:
      `release.yml` builds the platforms the tag names
      (`allsimd-<version>`: all; `-linux`: the source package and the
      Linux wheels; `-macos`: the macOS wheels) or the manual run's
      input, and counts what it chose to build. A capacity problem becomes
      a delay, not a failed release.
- [x] **10. No SBOM in the wheels**, which bundle libjpeg-turbo, libwebp,
      libtiff, FreeType and others; Pillow's `generate-sbom.py` describes
      Pillow. Fix: a script that renames Pillow's SBOM for this package,
      with Pillow as its ancestor, embedded in every wheel as Pillow does
      (PEP 770).
- [ ] **11. x86 users still compile.** The biggest user-facing gap, by
      design: an SSE4.1 wheel would silently lose AVX2. Run-time dispatch
      (one build that chooses SSE4.1 or AVX2 kernels when `_imaging`
      loads) is what makes x86 and Windows wheels possible; move it up
      from "Later" in `PLAN.md`.
