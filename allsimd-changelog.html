Changelog (Pillow-AllSIMD)¶

Pillow-AllSIMD’s changes, then those of Pillow-SIMD, which it forks.

13.0.0.post0 (unreleased)¶

Based on Pillow 13.0.0

  • The project is Pillow-AllSIMD (pillow-allsimd), a fork of Pillow-SIMD: the distribution name, the documentation and the credits say so; the fast mode variable is PILLOW_ALLSIMD_FAST (PILLOW_SIMD_FAST, its former name, still works)

  • Fast mode is on by default: the operations with a fast kernel (Gaussian blur, RGB <-> YCbCr, RGB -> HSV, transforms and rotate(), blend(), large downscales) give results within a few documented levels of Pillow’s. PILLOW_ALLSIMD_FAST=0 or Image.set_fast(False) selects the exact kernels, as before. Large downscales take the reduce() shortcut on 8-bit images only (32-bit sums overflow on I and F images), and leave a malformed box to resize()’s own error

  • Merged Pillow 13.0.0: security fixes, free-threading locks (the SIMD paths run inside them), vertical-first resampling and the MKS2013 and MKS2021 filters, which use the SIMD resample kernels (MKS2021 RGB 1/4: about 10x the 13.0 wheel on AVX2)

  • arm64: NEON again for the horizontal box blur of 4-byte images and the unsharp mask row, which beat the compiler’s code with GCC 12 and 14 (gaussian RGB 1.27x, unsharp RGB 1.31x on Cortex-A78AE); 13.0’s histogram loops on arm64 (1.1x)

  • Rank, median, minimum and maximum filters of 1-byte images up to 11x11 use a sorting network pruned for the rank, vectorised by the compiler: median 5 65x, rank 7 50x faster than Pillow 13.0 (2560x1600)

  • Rank filters read the image’s edges instead of an expanded copy (median 3 2.5x); ImageDraw: vector span fill and RGBA ink blend (filled shapes 1.6x to 2.3x), masked fills for text and bitmap(); floodfill in C (60x)

  • point(): XOR, AND and solarize tables as byte operations (ImageOps invert, posterize, solarize 3.3x), output not zero-filled; ImageEnhance contrast and brightness as lookup tables (1.5x)

  • PNG encoding: vector row filters (level 1 1.7x); RGB <-> YCbCr without table lookups (1.6x, 3.1x)

  • Text: rendered glyphs and their boxes are cached per font (text 5.9x, stroked text 17x, textbbox 2.1x)

  • Palette mapping (quantize, convert to an adaptive palette): a colour cache and, for max coverage, a vector nearest-entry search (1.2x to 1.7x)

  • Transposes and 90 degree rotations in register blocks (L 3.2x, RGB 1.4x); flips and rotate 180 by vector row reversal (RGB 1.4x, L 10x)

  • Resampling of F, I and I;16 images in vectors of doubles, every sum in the scalar code’s order (1.8x to 5.5x)

  • Arcs, chords and pie slices are clipped without allocating (1.25x); alpha_composite() with an offset composites in place (2.2x); tobytes() encodes in one chunk (1.9x)

  • Resize: the AVX-VNNI build no longer puts vpdpwssd in the horizontal pass, where each pixel is one long chain of additions: shrinks with long kernels (2560x1600 to 26x16) 1.3x to 1.6x faster, now level with AVX2; RGB in the portable build sums three channels, not four (1.2x, level with Pillow 13.0 for big shrinks)

  • Perspective transforms: the coordinates of a tile row are computed in one loop the compiler vectorizes, so the two divisions per pixel run several at once (1.4x RGB bilinear and bicubic, 1.8x L nearest, AVX2); quad transforms with the bilinear filter inlined (1.2x). Same output

  • RGB -> HSV: AVX2 kernel for 8 pixels, the same operations per lane as the SSE4 one; identical for all 16.7 million RGB values; 2.2x

  • RGB -> CMYK, L -> RGB/LA, RGB <-> RGBA a pixel at a time, which the compiler vectorizes (1.6x to 2.9x; the AVX2 build’s CMYK was 15% slower than SSE4); ImageChops add and subtract with scale 1 in integers, other scales by table, lighter and darker without clipping (add 1.6x)

  • BoxBlur, GaussianBlur, UnsharpMask: the passes of each direction run together, every horizontal pass on a row while it is in cache, the vertical ones in one sweep with a ring of rows per pass; AVX2 blurs two rows at once horizontally and 32 bytes per step vertically. Same output. AVX2: Gaussian RGB 2x, box blur 2.3x, unsharp mask 1.8x

  • Rank filters (min, max, median, any rank up to 11x11) on RGB, RGBA, CMYK, LA and other 4-byte modes run all bands in one pass instead of splitting and merging; min and max keep their row results in a ring of rows and vectorize both passes; 3x3 and 5x5 medians in registers (SSE4, AVX2, NEON; Devillard’s 99-comparator network for 5x5). RGB min/max 3x3 11x, median 3x3 5.3x, median 5x5 2.4x, L median 3x3 2.8x, median 5x5 2.5x (AVX2)

  • Images take transparent huge pages on Linux, as numpy arrays do: box blur 1.5x (its vertical pass), ImageChops lighter 1.6x, most passes over large images a few percent

  • x86: RGBa -> RGBA is exact (colour above alpha gave 0, alpha 0 gave colour 0); slightly slower

  • checks/simd_test_remote.sh runs the test suite per SIMD build in a container, on a remote host or locally, so the host’s Python version does not matter

  • Fast mode switch: PILLOW_ALLSIMD_FAST=1, Image.set_fast(), Image.get_fast(), Image.fast_mode() and the fast feature. Off by default; it lets operations use kernels whose results may differ from Pillow’s by small, documented amounts (design/SIMD_FAST_KERNELS.md)

  • Fast mode: GaussianBlur and UnsharpMask up to radius 6 apply Pillow’s three box passes as one kernel with 8-bit weights in one pass, with exact bands near the edges: within 3 levels of the exact result, closer to a true Gaussian, 3.3x (x86) and 3.2x (arm64) faster at radius 1

  • Fast mode: RGB, RGBA, RGBX <-> YCbCr with JPEG’s formulas at 14-bit coefficients and one rounding: within 1 level of the exact result and closer to the formulas (0.3% of values off by one, against 47%); to YCbCr 1.5x (x86) and 2.2x (arm64), back 1.3x and 1.7x

  • Fast mode: RGB, RGBA, RGBX -> HSV with the hue and saturation truncated exactly (one 32-bit float division each): the hue is 1 above the exact result for 0.3% of colours, saturation and value are the same; 2.9x (x86), 2.0x (arm64)

  • Fast mode: affine, perspective and quad transforms and rotate() with the bilinear and bicubic filters (L and 4-byte modes) take positions in fixed point and integer filters with one rounding: within 2 levels of the exact result, 0.6% of values off by one against float interpolation (exact: 41%); rotate bilinear 2.7x (x86) and 2.6x (arm64), bicubic 2.9x and 3.4x, perspective 2.1x and 1.9x, L rotate bilinear 2.8x and 1.9x (vertical first in 16-bit lanes, four pixels per AVX2 step, eight L pixels per step)

  • Fast mode: blend() with 0 < alpha < 1 interpolates in integers, alpha in 2^-15 units, rounded (pmulhrsw, vqrdmulh): within 1 level of the exact result, 1.7x (x86) and 4.1x (arm64)

  • Fast mode: resize() with the bicubic, Lanczos and MKS filters and no reducing_gap uses 3.0, so downscales of 6x and more shrink with reduce() first: within 2 levels at photo sizes, 1/8 Lanczos 1.9x (x86) and 2.5x (arm64)

  • BoxBlur with one pass each way and radii the direct kernel takes (integers up to 4, below 1): each row is blurred horizontally into a ring of rows just before the vertical pass reads it, instead of through a full temporary image; the same pixels (radius 1 2.1x, 2 1.7x, 3 1.5x, AVX2)

  • arm64: point() tables on 8-bit bands with NEON lookups (tbl, tbx) in the 256-entry tables, a row’s bands as planes so each table loads once (L 1.9x, RGB 1.3x, both now level with or ahead of OpenCV)

  • Fast mode: perspective positions in 32-bit floats from the exact integer sums (images below 32768 pixels a side), four lanes per division on SSE4 and NEON, eight on AVX2; still the same on every build (arm64 1.2x)

  • WebP: one-frame files decode straight into the image with libwebp’s simple API, without the animation decoder’s canvas and two copies (the same pixels; 1.38x, 2560x1600 RGB, now ahead of OpenCV)

  • JPEG: RGB images decode to 4-byte pixels in libjpeg-turbo’s colour conversion (JCS_EXT_RGBX) instead of being expanded row by row (1.05x); PNG: the “up” filter undone 16 bytes at a time (1.1x on such rows)

  • ImageDraw polygon outlines wider than 1 px keep the polygon’s inside as spans per row, from the same scan as its fill, instead of a mask of its bounding box: the same pixels, 1.1x for the benchmark’s ROI polygons and 1.7x for polygons 1400 px across

  • arm64: RGBa -> RGBA (and so RGBA resize and transforms) divides once per pixel instead of once per channel, with the same result for every colour and alpha (1.12x)

  • Pixel conversions written so that they vectorize under Python’s -fno-strict-overflow (RGBA -> RGB 1.9x, RGB -> RGBA 1.9x, L -> RGB 2.1x with AVX2); NEON loops for L -> RGB, RGB <-> RGBA and CMYK

  • ImageChops add and subtract with scale 1 and offset 0 as saturating vector additions (AVX2 1.8x, NEON 2.4x)

  • Rank filters: the 3x3 median in registers also at -O2 (Debian, Ubuntu and conda Pythons: 1.75x), minimum and maximum in one pass (1.4x AVX2, 1.3x NEON)

  • Box and Gaussian blur: radii below 2 and integer radii up to 4 without running sums, in SSE4, AVX2 and NEON (Gaussian RGB radius 1 1.7x on both; box radius 2 1.2x AVX2, 1.6x NEON; unsharp mask 1.2x AVX2, 1.5x NEON)

  • RGB <-> YCbCr: AVX2, and 16 pixels per step on NEON (AVX2 2.0x and 1.9x); RGB -> HSV on NEON (1.4x)

  • Kernel filters: kernels whose coefficients don’t fit 16 bits at 13 fractional bits (FIND_EDGES, CONTOUR, EDGE_ENHANCE) use the integer kernels at the highest precision that keeps them exact (2.2x AVX2, 2.0x NEON), and EDGE_ENHANCE and other kernels with half-integer coefficients now give the scalar build’s result on x86; 3x3 kernels for L images keep their coefficients in registers (1.1x AVX2)

  • Text: glyph advances cached for the basic layout (3.3x x86, 4.2x arm64); polygons: scan-line intersections sorted without qsort (1.25x)

  • ImageDraw: thin lines and rectangle outlines write their pixels directly again, as before Pillow 13.0, instead of through a function pointer per pixel (500 bounding boxes 2 px wide: 1.6x)

  • ImageDraw.polygon() with an outline wider than 1 px: the mask that keeps the outline inside the polygon covers only the polygon, not the whole image (100 ROI polygons on 2560x1600: 6.6x). Same pixels

  • arm64: rotate() and the affine, perspective and quad transforms with the bilinear and bicubic filters on RGB and RGBA images in NEON doubles: the scalar filters’ integer differences for the 4 bands of two rows in 16-bit lanes, converted exactly, then the same fused multiply-adds; two pixels at a time where their source pixels are inside the image. The same pixels; rotate bicubic RGBA 1.59x, RGB 1.32x, bilinear RGB 1.47x, RGBA 1.54x, perspective 1.25x to 1.30x, quad 1.37x (Cortex-A78AE)

  • arm64: alpha_composite() looks the scalar code’s per-pixel division up in a table of every source and destination alpha (128 KB, built on first use), with NEON for the rest: the same pixels, 1.25x; reduce() by 4x4 of 4-byte images in NEON pairwise sums (1.15x)

  • resize() of RGBA and LA images premultiplies the source rows inside the first resample pass and removes it from the rows of the last, where they are in the cache, instead of converting the whole image to RGBa and back. The same pixels; x86 1.1x to 1.7x (2048x1280 bilinear 1.68x), arm64 1.1x to 1.3x

  • arm64: RGBa -> RGBA (and so RGBA resizes) looks up 255 * c / alpha in a 64 KB table of the scalar code’s results, two pixels per 64-bit word: 1.7x on Cortex-A78AE, where the float kernel was bound by conversions (on x86 the table is slower than the vector kernels, which stay)

  • arm64, fast mode: RGB -> HSV computes the hue in 16-bit lanes with one division and takes the saturation from that table (1.67x); YCbCr -> RGB multiplies Cr and Cb in 16-bit lanes with rounding doubling multiplies (1.53x). The same pixels as before; both now faster than OpenCV

  • MinFilter and MaxFilter of the same size: the row ends clamp the pixel index instead of copying each row into a padded buffer, and the 3x3 filters skip the loop over the sources (3x3 RGB: 1.1x to 1.2x AVX2, 1.4x NEON)

  • Box blur radii 1 to 4 without running sums: the sum’s sources unrolled per radius (radius 2 RGB: 1.46x AVX2 at -O3)

  • 32-bit x86: the SIMD builds do floating point in SSE registers (-mfpmath=sse); on the x87 unit a transform’s pixels could depend on the code around them. -C simd=native passes -mcpu=native on POWER and is refused on RISC-V with a hint. The portable build passes the test suite on riscv64, ppc64le, s390x, armv7 and 32-bit x86 (design/OTHER_ARCHITECTURES.md); checks/simd_test_remote.sh takes those platforms, and checks/simd_hashes.py hashes I and F pixels little-endian, so big-endian builds compare

  • Fast mode: resize() of 8-bit images with 4-byte pixels fuses the two passes through a ring of rows, keeps the horizontal sums to 2^-6 levels and multiplies in 16 bits in the vertical pass (pmulhrsw, vqrdmulh): within 1 level of the exact result and closer to a float resize; upscales 1.16x to 1.28x (x86) and 1.31x to 1.47x (arm64), downscales to 1.20x on arm64 and within 4% on x86. The same pixels on every build

Build

  • -C simd=auto|sse4|avx2|avxvnni|native|native512|neon|disable option; flags chosen per target architecture; SSE4.1 baseline on x86 (was SSE4.2). native builds for the build machine’s CPU (-march=native, float contraction off), native512 also prefers 512-bit vectors; both only run on CPUs like the build machine’s

  • AVX-VNNI build (-C simd=avxvnni): the 16-bit multiply-add of the resample and integer filter kernels becomes one vpdpwssd. Same output; integer filters on RGB 1.3x to 2.1x faster than AVX2

  • arm64: NEON kernels; other architectures build portable C code

New and faster kernels

  • Resize of 1-byte images (L): SIMD horizontal pass (SSE4, NEON), 2.4x to 8x faster on x86, 2.5x to 3.3x on arm64

  • Reduce: 1x2, 2x1, 2x2 about 2x faster on x86; 2x2 and 4x4 for 1-byte images on SSE4 and NEON, 6x to 10x faster; NEON for 4-byte images with horizontal factors up to 512 (1.6x to 4.5x on arm64); restored 4x4 and 5x5 for 1-byte images

  • Filter: integer kernel for L images, up to 2x faster; on arm64 NEON integer kernels and NEON float kernels for 4-byte images (FIND_EDGES on RGB 1.7x). Like the x86 float kernels, the float ones can differ by 1 from the scalar code for inexact coefficients

  • BoxBlur, GaussianBlur: vertical pass without transposes, up to 1.8x faster; on x86 1-byte images are blurred four rows at a time, 1.9x to 3x

  • UnsharpMask: SIMD post-pass on x86, about 1.7x faster

  • ColorLUT: NEON kernel (1.5x), output identical to the scalar code

  • ImageChops.multiply, screen: exact division by 255 without a divide; SSE4, AVX2 and NEON. 6.4x to 12x faster on x86, 3.4x on arm64

  • RankFilter, MinFilter, MaxFilter, MedianFilter on 1-byte images: a sorting network for 3x3 windows (any rank) and row-then-column minimum and maximum for any size, 14x to 130x faster; the GIL is released

  • Filter with integer kernels on L images: AVX2 path, 32 pixels per step, 2x faster than SSE4 (2.2x with AVX-VNNI); output unchanged

  • Quantize with median cut or maximum coverage, convert(“P”, ADAPTIVE): the color hash table takes its nodes from blocks instead of one malloc each; the same chains, so the same palette and pixels. 1.7x faster on a 2560x1600 image of random colors

  • RGB to HSV: SSE4 kernel for 4 pixels with the float and double steps of the scalar code, and fmod(h, 1.0) replaced by its exact equivalent for the range h is in. 5.4x faster than upstream on SSE4, 1.4x in the scalar build; output identical for all 16.7 million RGB values

  • Filter with 3x3 float kernels on L images (CONTOUR, FIND_EDGES): AVX2 path, 8 pixels per step, 1.9x faster than SSE4; output unchanged

  • Rotate and transform (affine, perspective, quad, mesh): the output is computed in 64x64 tiles, which keeps the source rows in cache; bilinear and bicubic filters for 3- and 4-band images take all channels in one AVX2 vector of doubles (two with SSE4). Output identical. On x86, rotate 30 degrees 2560x1600 RGB: nearest 3x to 4.6x, bilinear 1.6x (SSE4) to 2x (AVX2), bicubic 1.4x to 2.2x; perspective 2x to 2.5x. The tiles alone make the scalar build 1.2x (bilinear, bicubic) to 4x (nearest) faster

  • ModeFilter: the window histogram is updated by columns, and windows of fewer than 16 values check only their own values; 13x faster for size 3, 3.4x to 4.8x for sizes 5 to 17; output unchanged; the GIL is released

  • Histogram of 8-bit images: counts split over several tables, 1.2x to 2.4x faster

  • ImageChops.offset: two row copies instead of a modulo per pixel, 13x faster

  • RGB pack and unpack (frombytes, tobytes, codecs): SSE4 and NEON, 1.1x to 1.7x faster

  • arm64: alpha composition and the vertical blur pass use the portable C code, which GCC vectorises better than the previous NEON kernels did

  • Released the GIL in AlphaComposite, Bands, Blend and Chops

Fixes

  • BoxBlur, GaussianBlur: fixed swapped channels for single-axis blurs on 4-byte modes; fixed reads past 1-pixel lines

  • Filter: fixed I;16 images going to the 8-bit kernel

  • Reduce: fixed 1x3 rounding

  • AlphaComposite, Convert: results no longer depend on the pixel’s position in the row

  • ImageChops.offset: fixed reads and writes past the end of each row for I;16 images

  • From Pillow 13.0: I;16 filters keep the high byte and clamp to 0..65535; BoxBlur and GaussianBlur reject NaN, infinite and >= 2**31 radii; ImagingExpand’s size check no longer overflows or divides by zero; masked histograms of LA images count the alpha band

The changelog of Pillow-SIMD (https://github.com/uploadcare/pillow-simd), by Alexander Karpinsky and contributors, up to the fork.

9.5.0.post2 & 9.4.0.post2 & 9.3.0.post2 & 9.2.0.post2 & 9.1.1.post2 & 9.0.0.post3¶

  • Fixed color overflow in LUT processing

9.0.0.post1¶

  • Fixed possible overflow in LUT processing

  • Restored compatibility with Visual C Compiler

7.0.0.post4¶

  • Filter: fixed wrong offset handling for 3x3 single-band version

7.0.0.post3¶

  • ColorLUT: fixed potential access violation, up to 2x faster

7.0.0.post2¶

  • ColorLUT: SSE4 & AVX2

7.0.0.post1 & 6.2.2.post1 & 6.1.0.post1 & 6.0.0.post2¶

  • Bands: access violation in getband in some environments

7.0.0.post0¶

  • Reduce: SSE4

6.0.0.post1¶

  • GCC 9.0+: fixed unaligned read for _mm_cvtepu8_epi32 and _mm256_cvtepu8_epi32 functions.

6.0.0.post0 and 5.3.0.post1¶

  • Resampling: correct max coefficient calculation. Some rare combinations of initial and requested sizes lead to black lines.

4.3.0.post0¶

  • Float-based filters, single-band: 3x3 SSE4, 5x5 SSE4

  • Float-based filters, multi-band: 3x3 SSE4 & AVX2, 5x5 SSE4

  • Int-based filters, multi-band: 3x3 SSE4 & AVX2, 5x5 SSE4 & AVX2

  • Box blur: fast path for radius < 1

  • Alpha composite: fast division approximation

  • Color conversion: SSE4 RGB-to-L conversion, fast division in RGBa-to-RGBA conversion

  • Resampling: optimized coefficients loading

  • Split and get_channel: SSE4

3.4.1.post1¶

  • Fixed a critical memory error for some combinations of source and destination sizes.

3.4.1.post0¶

  • Numerous resampling optimizations, including a 16-bit intermediate color representation and heavy unrolling.

3.3.2.post0¶

  • Maintenance release

3.3.0.post2¶

  • Fixed an error in RGBa -> RGBA conversion

3.3.0.post1¶

Alpha compositing¶

  • SSE4 and AVX2 fixed-point full-loading implementations. Up to 4.6x faster.

3.3.0.post0¶

Resampling¶

  • SSE4 and AVX2 fixed-point full-loading horizontal pass.

  • SSE4 and AVX2 fixed-point full-loading vertical pass.

Conversion¶

  • RGBA -> RGBa SSE4 and AVX2 fixed-point full-loading implementations. Up to 2.6x faster.

  • RGBa -> RGBA AVX2 implementation using gather instructions. Up to 5x faster.

3.2.0.post3¶

Resampling¶

  • SSE4 and AVX2 float full-loading horizontal pass.

  • SSE4 float full-loading vertical pass.

3.2.0.post2¶

Resampling¶

  • SSE4 and AVX2 float full-loading horizontal pass.

  • SSE4 float per-pixel loading vertical pass.

2.9.0.post1¶

Resampling¶

  • SSE4 and AVX2 float per-pixel loading horizontal pass.

  • SSE4 float per-pixel loading vertical pass.

  • SSE4: up to 2x for downscaling and 3.5x for upscaling.

  • AVX2: up to 2.7x for downscaling and 3.5x for upscaling.

Box blur¶

  • Simple SSE4 fixed-point implementations with per-pixel loading.

  • Up to 2.1x faster.
